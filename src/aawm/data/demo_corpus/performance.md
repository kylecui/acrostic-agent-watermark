# AAWM 性能基准

> 实测环境：沙箱 Ubuntu 22.04 / Python 3.11.1 / 单线程 / 2026-08-19
> 脚本：内嵌计时（time.perf_counter，3 次平均）

---

## 1. 嵌入/检测延迟

测试文本：Gutenberg 英文文学语料（Pride and Prejudice 正文片段），`bias=1.0`，含信道 A 签名。

| 文本长度（词） | 嵌入耗时 | 检测耗时 | 存在性得分 | 词典命中 |
|---|---|---|---|---|
| 200 | 7.2 ms | 6.3 ms | 13.3 | ~27 |
| 600 | 8.1 ms | 6.8 ms | 36.5 | ~85 |
| 1200 | 10.0 ms | 6.7 ms | 50.6 | ~170 |
| 2400 | 13.7 ms | 8.2 ms | 74.2 | ~340 |

**结论**：
- 嵌入耗时近似 O(n)，约 **3-6 ms/千词**
- 相对开销：LLM 生成同样文本需 2-30 秒，水印嵌入 < 0.1%（设计目标 G8 要求 <10%）
- 存在性得分随文本长度线性增长——这就是自适应阈值（`adaptive_factor × √n`）的依据

## 2. 内存

| 组件 | 内存 |
|---|---|
| Watermarker 实例（不含词典） | ~1 KB |
| 进程级词典构建（英文，模块加载时一次） | ~50 MB 峰值 |
| 进程级词典构建（中文，懒加载） | ~40 MB 峰值 |

词典构建发生在 `GreenlistCodec.__init__`（稳定化 + 分带索引），每个 codec 实例重复构建——**流式场景每个流创建新 codec 会有重复开销**，建议长生命周期进程复用 codec（当前 Facade 每次 embed/trace 新建，v0.7 优化点）。

## 3. 流式场景

句子级缓冲重写（StreamingWatermarker）：
- **额外延迟**：一句的长度（用户看到输出的时间延后一个句子）
- **吞吐**：与整文本嵌入相同（总工作量不变，只是分批）
- 内存：缓冲区 = 当前未完成句子的长度（通常 < 200 字符）

## 4. 检测服务并发

FastAPI + uvicorn（单 worker）：
- 检测是 CPU 密集（纯 Python 同义替换 + 统计），**async 端点但实际是同步计算**
- 单实例 QPS 估算：600 词文本检测 6.8ms → 理论 ~145 QPS
- 高并发建议：多 worker（uvicorn --workers N）或横向扩容，检测无状态（除了注册库只读）

## 6. 已知瓶颈与优化路线

| 瓶颈 | 影响 | 状态 |
|---|---|---|
| codec 重复构建 | 每次 embed/trace 重建词典索引（~5ms）| v0.7 计划：实例级缓存 |
| 纯 Python 分词/替换 | 千词毫秒级 | 可接受；如需 10x 提速可上 Cython/正则预编译 |
| 检测端同步阻塞 | async 端点内联计算 | 高并发时用多 worker 规避 |
| 中文分词（前向最大匹配） | O(n·maxlen) | 可接受；词典哈希已优化 |
