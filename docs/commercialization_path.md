# AAWM 商业化路径研究（开源核心 + 商业授权）

> **状态**：研究报告 v1（2026-09-08）· 决策输入，非法律意见
> **决策关联**：PRODUCT_GAP_RECOMMENDATIONS.md §8「作者决策记录」决策二
> **目标**：在"开源一部分 + 保留商业授权可能性"的约束下，给出 License 策略、
> 组件切分边界、执行路径与风险清单。

---

## 1. 结论先行

**推荐路径：Open-Core（开放核心）+ 商业组件独立许可证**，即：
- 现有核心（算法 + CLI/SDK/server/适配器）**保持 MIT**——这是七轮验证建立信任飞轮的根基，动它会毁掉"逐字节可核验"的资产
- 新增的高价值组件以**独立模块 + 独立许可证**（专有 / BUSL-1.1 / 双授权）发布，**不混入 MIT 包**
- 禁止在 MIT 代码文件里夹带商业逻辑（文件级隔离），否则污染整个 MIT 授权面

**为什么不是"整体改 license"**：v0.11.1–v0.13.1 已按 MIT 语义发布到 PyPI（pyproject 声明 MIT），既有分发不可追溯变更。整体改 Apache-2.0/双授权需要重发历史版本，且与已声明的 MIT 冲突。**唯一干净的做法是"向前看"——存量保持 MIT，增量走独立授权。**

## 2. 现状盘点（License 事实核查）

| 项 | 现状 | 问题 |
|---|---|---|
| LICENSE 文件 | **仓库无 LICENSE 文件**（`ls LICENSE*` 空） | 最严重缺口：GitHub 不显示 license 元数据（API 返回 null），法律上代码"保留所有权利"状态不明 |
| pyproject.toml | `license = {text = "MIT"}` | 声明了 MIT 但无 SPDX 标识符 |
| PyPI | `info.license = MIT`（继承 pyproject） | 已按 MIT 分发 v0.11.1/v0.12.0/v0.13.0/v0.13.1 |
| README | "许可证：待定（拟 MIT 或 Apache-2.0）" | **与 pyproject/PyPI 矛盾**——文档说待定，元数据说 MIT |
| 作者构成 | 2 个 commit 身份（Cui Yin / PEtFiSh=kylecui），疑同一人 | 单作者项目 → license 决策自主权完整，无需征询外部贡献者 |
| 仓库可见性 | public，0 star/0 fork | 采用率尚在起步，license 修正的**窗口期成本最低** |

**法律含义**（非法律意见，需律师复核）：
- 已发布的 v0.13.1 等版本在 PyPI 元数据声明 MIT——下载者可能主张 MIT 许可。追溯改授风险高。
- 但仓库本体无 LICENSE 文件 + README 写"待定"，说明**从未正式完成 MIT 授权行为**——这是修正窗口：补 LICENSE 文件可以明确"从此版本起正式 MIT"，或为未来商业组件预留独立授权空间。
- 0 star/0 fork 意味着**无下游用户依赖惯性**，现在是定 License 策略的最佳时点（越晚越被动）。

## 3. 候选 License 策略对比

| 策略 | 形态 | 开源部分 | 商业部分 | 优点 | 代价/风险 |
|---|---|---|---|---|---|
| **A. Open-Core（推荐）** | 核心 MIT + 商业组件独立许可 | 现有全部代码 | 新组件（见 §4） | 信任飞轮不动；清晰边界；业界主流（GitLab/Element） | 需自律：商业组件不得"掏空"核心价值；社区贡献需 CLA |
| B. 双授权（Dual-License） | 同一代码 MIT + 商业授权二选一 | 同一份 | 同一份（卖 license） | 单代码库维护 | 需 CLA + 全量贡献者授权（现在单人可行，多人后极难）；与已发布 MIT 分发冲突 |
| C. BUSL-1.1 + 转换 | 源码可用但限制生产使用 | — | — | 保护更强 | 非 OSI 开源，劝退社区；与"开源一部分"目标冲突 |
| D. 维持纯 MIT | 全开源 | 全部 | 无 | 最简单 | 放弃商业化；靠捐赠/咨询变现（弱） |
| E. 平台/咨询变现（不开新 license） | 纯 MIT + 付费服务 | 全部 | 服务（部署/定制/培训） | 零授权改动 | 收入天花板低；与开源社区竞争 |

**本报告推荐 A 为主干**，理由：
1. 单作者、零下游 → 现在切 Open-Core 的摩擦最小；
2. 七轮验证的信任资产全部在"MIT 全开源可复现"上，A 完整保留；
3. 商业组件以**新增独立目录**承载，MIT 包体积与验证基线（399 测试）完全不受影响。

## 4. 组件切分边界（哪些开源 / 哪些商业）

判定原则：**凡七轮验证覆盖过的能力一律开源**（验证报告 §13.4 结论依赖它）；
**未验证的新增量**才有资格进商业层。切分按"文件级隔离"执行。

### 4.1 开源层（MIT，保持现状）

- 算法内核：keys/coding/greenlist/content/binding/anchor/collocation/stats/synonym_data/transforms/zh/decoder/embedder/verifier
- 运维：audit / meta_store（File+SQLite 双后端）/ server（api+metrics）/ cli / proxy
- 插件：facade/middleware/keystore/registry/context/streaming + 全部 5 适配器
- 数据：zh_zero_cost.json / en_zero_cost.json / demo_corpus（标定与复现必需）
- 验证资产：tests/（399 项）、docs/、CHANGELOG——**这些是信任飞轮的燃料，绝不进商业层**

### 4.2 商业层候选（新组件，独立许可）

按"客户愿意付费"与"不掏空核心价值"双重标准筛选：

| 候选组件 | 价值主张 | 技术现状 | 优先级 |
|---|---|---|---|
| **聚合水印缓冲层**（会话级） | 短文本拼装成长文本再嵌——补上能力窗口短板，是差距文档 P0-3 的 B 方案 | 仅设计未实现（2026-08-28 记忆） | **P0**（最可能让客户为"短文本场景"付费） |
| **大规模 meta_store**（对象存储 + 索引） | 百万级 meta 的检索后端（find-meta 分布式） | 现状 SQLite/文件，规模未验证 | **P0**（企业部署刚需） |
| **合规/取证导出套件** | 审计报表、证据链固化、与 SIEM 对接 | 审计已有 JSONL，导出未做 | P1 |
| **代理网关企业版**（多租户/SSO/策略） | 平台级代理网关管理 | 现状单租户（proxy/） | P1 |
| **SLA 支持 / 私有化部署服务** | 非代码，服务形态 | — | 随客户走 |

### 4.3 明确不进商业层的

- reliability 分级 / abstain / 弱嵌入警告——这些是**安全护栏**，若进商业层等于"免费版故意给出危险结论"，会摧毁可信度，商业层只做增量便利，不做能力阉割。

## 5. 执行路径（Roadmap）

### Phase 0（立即，1 周内）：License 基建补课

1. **补 LICENSE 文件**（MIT 全文）到仓库根目录，消除"待定"矛盾——README 许可证段改为正式 MIT 声明
2. pyproject 用 SPDX 标识：`license = "MIT"`（替换 `{text = "MIT"}`）
3. **新增 CLA（贡献者许可协议）**：从第一个外部贡献者起要求签署——这是未来双授权/Open-Core 的必选项（参考 GitLab CLA）
4. README 增加"商业组件"预告段：声明核心 MIT、未来增量可能独立授权——**透明预告避免社区 surprise**

### Phase 1（近期）：商业组件 P0 立项

1. **聚合水印缓冲层**作为第一个商业组件试点（`src/aawm_enterprise/` 独立目录 + 独立 `LICENSE.enterprise`）
2. 与核心的接口：复用 facade 的 embed/trace 公共 API，缓冲逻辑独立实现——核心不 import 商业层，商业层 import 核心（单向依赖，保证 MIT 纯净）
3. 交付形态：`pip install aawm-enterprise`（独立包）或私有 index——**绝不混入 acrostic-agent-watermark 包**

### Phase 2（客户出现后）：定价与渠道验证

- 定价锚点：内部审计/防泄露场景（验证判定"推荐"）+ 合规导出 = 企业合规预算
- 渠道：README 不推商业（保持开源调性）；商业入口放独立 landing 页/邮件
- 是否引入平台路线（差距文档 §6 路线 A）：等 2-3 个真实客户信号再决定双授权，不提前投入

## 6. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 已发布 MIT 版本的追溯授权争议 | **高** | 补 LICENSE 明确"自某 commit 起正式 MIT"；咨询律师；因 0 下游影响最小 |
| Open-Core 边界模糊（社区觉得核心被掏空） | 中 | 严守 §4.3：护栏能力永不商业；商业只做"便利层" |
| 外部贡献者无 CLA 导致未来双授权受阻 | 中 | Phase 0 即上 CLA |
| 商业组件复用核心内部 API 形成隐式耦合 | 中 | 单向依赖纪律 + CI 检查（核心不 import 商业包） |
| PyPI 包名混淆（aawm-enterprise 与主包） | 低 | 文档明确二者关系 |
| BUSL/专有许可吓退潜在采用者 | 低（当前） | 商业组件默认不阻碍核心采用路径 |
